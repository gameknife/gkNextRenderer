# 高 Token 效率的 Agent 工程开发方式

本文总结 gkNextEngine 使用 Codex 持续开发时形成的一套高 Token 效率工作方式，供团队内使用
Coding Agent 的同事直接复用。

这里的“节省 Token”不是要求 Agent 少读代码、降低推理等级或省略验证，而是减少三类浪费：

1. 重复解释已经存在的项目背景；
2. 因任务模糊产生的搜索、澄清和错误实现；
3. 方案已经被证伪后仍继续修补产生的返工。

一句话概括：

> **让上下文可复用，让每次输入都提供新的决策信息，让验证尽快终止错误方向。**

## 1. 实际数据说明了什么

截至 2026-07-13，本机 session 存档中有 188 个任务包含完整 Token usage，约 95% 的任务属于
gkNextEngine / gkNextRenderer。下表是这批 session 的一次快照。统计使用每个 session 最后一个
累计 `total_token_usage`，并扣除了 fork 复制的父 session 历史，算法见附录。

| 指标 | 约值 | 解读 |
| --- | ---: | --- |
| 累计输入 Token | 21.6 亿 | Agent 多次调用模型时，完整上下文会重复计入 |
| 缓存输入 Token | 20.5 亿 | 已处理过的稳定前缀和连续对话占绝大部分 |
| 输入缓存命中率 | **94.8%** | 只有约 5.2% 的输入是非缓存输入 |
| 非缓存输入 Token | 1.12 亿 | 本次真正新增或缓存未命中的输入 |
| 输出 Token | 约 725 万 | 包括可见回复、工具调用、推理及不可见格式 Token |
| 每条用户消息触发的工具调用 | 约 28 次 | Agent 实际执行量并不低 |
| 首条任务消息长度中位数 | 93 字符 | 起始任务短，但通常包含明确范围和目标 |
| 后续消息长度中位数 | 34 字符 | 后续主要提供新证据或决策，不重复背景 |

这组数据最重要的结论不是“提示词越短越省”，而是：

> **在完成大量代码搜索、修改、构建和验证的同时，绝大部分输入上下文得到了复用。**

`cached_input_tokens` 是 `input_tokens` 的子集，不能与输入再次相加；`reasoning_output_tokens`
也是 `output_tokens` 的子集。字段语义可参考 OpenAI 的
[Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching#requirements) 与
[Token Counting](https://developers.openai.com/api/docs/guides/token-counting#understand-output-token-counts)。

缓存率不能直接换算为 Codex 订阅额度、API 费用或实际算力。不同模型、推理等级和产品额度可能有
不同权重。团队比较时必须使用同一时间段、模型和统计口径。

## 2. 高 Token 效率的心智模型

可以把一次 Agent 任务的效率粗略理解为：

```text
有效工程产出
──────────── ≈ 上下文复用 × 决策信息密度 × 验证确定性
 Token 消耗              澄清成本 × 错误探索 × 返工距离
```

这不是计费公式，只是帮助判断工作方式的模型：

- **上下文复用**：Agent 是否一直在熟悉的仓库、规则和连续任务中工作；
- **决策信息密度**：用户每次输入是否带来了范围、证据、边界或明确选择；
- **验证确定性**：Agent 能否通过一条命令或一个断言判断成功；
- **澄清成本**：Agent 是否频繁停下等待局部实现选择；
- **错误探索**：Agent 是否必须从整个仓库猜问题在哪；
- **返工距离**：错误方向从出现到被发现之间改了多少代码。

下面各节分别降低这些成本。

## 3. 把稳定知识放在仓库里

### 3.1 用 `AGENTS.md` 保存长期规则

不要在每个 session 重新解释以下内容：

- 项目架构和依赖方向；
- 构建、运行、测试命令；
- 代码风格和禁止事项；
- 不同改动范围对应的验证方式；
- 成功日志、截图和报告的位置。

gkNextEngine 将这些信息集中在 [`AGENTS.md`](../../AGENTS.md)。因此任务可以直接写：

```text
修复 Engine 层的这个问题，并按仓库规则验证。
```

Agent 已经知道 Engine 改动默认构建：

```powershell
./gnb.bat build gkNextRenderer gkNextUnitTests
```

而不是每次都让用户重复完整构建说明，或让 Agent 无差别执行全量构建。

`AGENTS.md` 应保存稳定规则，不要塞入某个任务的一次性需求。频繁改写长前缀也会降低上下文复用。

### 3.2 用设计文档保存复杂任务上下文

复杂任务先产出 `docs/designs/` 或 `docs/plans/` 文档，再由后续 session 执行。这样做不只是方便交接，
也把大量背景变成稳定、可按需读取的外部记忆。

真实流程示例：

1. 分析 `VulkanBaseRenderer` 架构和渲染正确性；
2. 让不同模型分别审核；
3. 综合审核结果，写出
   [`vulkan-base-renderer-architecture-refactor-plan.md`](../plans/vulkan-base-renderer-architecture-refactor-plan.md)；
4. 新 session 只需输入：

```text
根据 docs/plans/vulkan-base-renderer-architecture-refactor-plan.md
这份详尽的重构计划开始执行。
```

与在一个超长对话里反复回忆目标相比，这种方式有四个好处：

- 规划结果可以审核和修订；
- 执行 Agent 不需要重新推导已确定的决策；
- session 中断后可以从文档恢复；
- 不同 Agent 共享同一事实来源。

一份可执行计划至少应包含：目标、非目标、现状证据、架构约束、分阶段任务、每阶段验收方式、风险与
回退条件。不要只写愿景或文件清单。

## 4. 写“高决策密度”的任务输入

短提示词本身不会显著节省一个大型 Agent 任务的 Token。真正有效的是，在较短输入中同时提供：

```text
现象 + 范围 + 暂定假设 + 目标行为 + 不变量 + 验证方式
```

不要求每次六项齐全，但已知的信息不要省略。

### 4.1 实例：渲染残影

低信息输入：

```text
第二视口有残影，请修复。
```

实际使用过的高信息输入：

```text
gkNextEditor 的 CameraView 这类非主视口 view，motion vector 看起来没有生效，
导致 reproject 残影，请定位并解决问题。
```

第二种写法多提供了四个决定搜索方向的信息：

- 出问题的程序是 `gkNextEditor`；
- 范围是非主视口 `CameraView`；
- 表现位于 reproject；
- 怀疑 motion vector，而不是材质、相机本身或 swapchain。

“看起来”“怀疑”不会误导 Agent，因为它明确表示假设而不是既定结论。

### 4.2 实例：只在特定配置出错

低信息输入：

```text
wireframe 深度不对。
```

高信息输入：

```text
目前 wireframe 只有在 native upscaler 下可以正常绘制。
启用 upscaler 后，wireframe 的 depth buffer 无法对齐，导致绘制错误。
```

这里最有价值的信息是对照组：native 正常、upscaler 异常。它把搜索范围直接压缩到分辨率、viewport、
depth 映射和 compose 链路。

### 4.3 实例：性能问题

低信息输入：

```text
优化一下构建速度。
```

实际任务先列出了观察：

```text
1. 每个 application 的链接时间很长；
2. gnb build xxx yyy zzz 时，依赖库每个 target 都会重新过一次；
3. 某些编译项可能可以从 application 清除；
4. 可以评估扩大 unity build 范围；
5. 多 target 编译时并行程度看起来不高。
```

这不是要求 Agent 机械实现五个猜测，而是提供五条待验证线索。Agent 可以先 profile，再判断问题应该在
CMake、链接结构、target 依赖还是 `gnb` 调度层解决。

### 4.4 实例：人类已经完成关键实验

```text
最新实测下来，r.drawSubmitMode = 1 在各平台都支持良好。
可以让它成为引擎唯一 draw mode，完全移除 MDI 方式及相关 cvar、判断和 buffer。
```

“各平台实测通过”替 Agent 完成了一个昂贵且难以从静态代码得出的决策。此时任务不再是“比较两个
方案”，而是“删除已经失去价值的兼容分支”。

### 4.5 实例：明确架构不变量

在一次 Engine 模块化改造中，实际反馈不是笼统地说“依赖关系不太好”，而是直接给出允许的方向：

```text
Module 只能单向依赖 NextEngine；Application 依赖 Module 和 NextEngine。
NextEngine 反向依赖 Module 是错误的。
```

这类信息应由熟悉项目目标的人明确给出。否则 Agent 可能得到一个能够编译的局部方案，却把可选模块
重新焊回核心层，随后需要用更多 Token 才能发现和逆转架构退化。

## 5. 人和 Agent 各自做最擅长的工作

高效协作不是把所有判断交给 Agent，而是合理分工。

### 人更适合提供

- 实机画面是否正确；
- 操作手感、UI 密度和产品审美；
- profiler 中最昂贵的函数；
- 哪个平台、配置或场景可以复现；
- 架构中绝不能破坏的依赖方向；
- 方案是否值得继续投入。

### Agent 更适合完成

- 跨文件搜索和调用链梳理；
- 将现象映射到代码路径；
- 机械但范围较大的重构；
- 构建、测试和脚本化验证；
- 汇总多个实现方案的影响面；
- 更新文档和删除失效路径。

真实例子：当 GPU profiler 已经指出 ImGui 顶点组装、`GetComponent` 或 A-Trous 迭代开销时，把具体
热点和触发规模交给 Agent，比只说“FPS 低”能少走大量错误路径。

推荐反馈格式：

```text
现象：发生了什么
对照：什么配置正常，什么配置异常
范围：程序、场景、平台、渲染管线
证据：日志、profile、截图或可复现步骤
判断：目前怀疑什么，置信度如何
目标：修复后必须保持什么行为
```

## 6. 对可逆任务给予连续授权

Agent 频繁停下来询问局部选择，会产生重复上下文、额外解释和等待。对于已有计划、可通过 Git 回退、
验收命令明确的任务，可以一次授权连续推进。

真实任务写法：

```text
根据 docs/designs/agent-validation-input-driver.md 开始实现。
尽量自主决策，一口气把计划做完再人工验证。
```

更完整的团队模板：

```text
根据 <计划文件> 执行 <阶段或完整计划>。

授权：局部实现和已有模式内的重构可自主决定。
不变量：<依赖方向 / 兼容行为 / 不可修改范围>。
验证：每阶段执行 <命令或断言>。
停止条件：只有出现不可逆操作、目标冲突或无法从代码判断的产品选择时才暂停。
```

连续授权不等于不汇报、不验证或允许扩大范围。它只是把“每个局部变量怎么命名”之类的选择留给
Agent，把人工注意力保留给架构和产品判断。

### 什么时候继续当前 session

- 仍在处理同一个目标；
- 新问题是刚才修改的直接后果；
- 当前代码路径和验证上下文仍然有用；
- 只是在进入同一计划的下一阶段。

### 什么时候新开 session

- 目标已经从修 bug 变成新的架构设计；
- 任务属于另一个子项目；
- 需要独立审核，避免被原实现思路锚定；
- 当前任务已经完成并形成了可引用的计划或提交。

原则不是“永远使用长 session”，而是**一个连续目标使用一个热上下文，不同目标通过稳定文档交接**。

## 7. 把验证系统当作 Token 优化设施

没有确定验证方式时，Agent 会不断读取日志、猜测运行状态、请求人工观察。gkNextEngine 将常见验收
固化为短命令：

### 目标构建

```powershell
./gnb.bat build gkNextRenderer gkNextUnitTests
./gnb.bat build AirportSim
```

只构建受影响目标，减少等待、无关错误和大段编译日志进入上下文。

### 稳定帧截图

```powershell
./gnb.bat shot --scene assets/models/playground.glb
./gnb.bat shot --target AirportSim --ui
```

固定输出路径、隐藏窗口、稳定帧和自动退出，让 Agent 可以自己完成视觉检查。

### 输入驱动与断言

```powershell
./gnb.bat validate --script assets/agentscripts/smoke.agentscript.json
```

交互状态通过脚本进入，结果通过断言和 JSON report 判断，不需要多轮描述“点击这里以后应该看到
什么”。设计背景见
[`agent-validation-input-driver.md`](../designs/agent-validation-input-driver.md)。

### 明确成功信号

```text
uploaded scene [...] to gpu
```

Agent 不必通过一大段日志猜测程序是否已经正确启动。

一条稳定、机器可读的验证命令，通常比继续优化提示词更能节省长期 Token。

## 8. 快速结束错误方向

最昂贵的 Token 往往不是首次实现，而是试图挽救错误架构。

真实案例中，曾尝试简化 `StreamlineIntegration`，但修改后 DLSS 完全失效。最终决策是：

```text
回退本会话的所有修改，目前方向完全错了。
```

这比继续在错误抽象上修补更高效。推荐采用以下规则：

1. 开始高风险改动前保留干净提交或清晰 diff；
2. 每完成一个可独立验证的阶段就建立提交检查点；
3. 一旦核心假设被证伪，先回到最后正确检查点；
4. 重新写问题定义，不在失败实现上叠加第二套补丁；
5. 回退时只回退本任务产生的修改，不覆盖其他人的工作区变更。

另一个常见情况是“修复层级不对”。构建过滤问题曾被明确纠正为：

```text
不对，要从 CMakeLists 上过滤掉这个问题，而不是 gnb 上。
```

及时指出问题所属层，比继续讨论当前补丁的局部写法更有价值。

## 9. 常见低效模式

| 低效模式 | Token 为什么浪费 | 改进方式 |
| --- | --- | --- |
| “看看有没有问题” | Agent 不知道行为标准和重点 | 指定范围、风险类型和验收目标 |
| 每个 session 重述项目架构 | 稳定背景反复进入新输入 | 写入 `AGENTS.md` 或 guide |
| 直接粘贴完整构建日志 | 大量无关输出污染上下文 | 提供首个错误、目标名和完整日志路径 |
| 复杂任务直接开始写代码 | 架构选择在实现中反复推翻 | 先写并审核 design/plan |
| 每个局部选择都要求三套方案 | 决策轮次多于实现轮次 | 给出边界，授权 Agent 选择局部方案 |
| 一个 session 混入无关目标 | 缓存仍命中，但相关信息密度下降 | 新目标新 session，以文档或提交交接 |
| 无差别全量构建 | 等待长、日志大、无关失败多 | 按影响范围 targeted build |
| 错误方向上持续打补丁 | 每轮都扩大上下文和回退成本 | 核心假设失败时整体回退 |
| 只说“还是不对” | Agent 不知道错误发生了什么变化 | 给出当前现象和与上一版的差异 |
| 要求长篇过程汇报 | 输出本身占用 Token，且会进入后续上下文 | 只汇报决策、风险和验证结果 |

## 10. 可直接复用的任务模板

### 10.1 执行已有计划

```text
根据 <docs/path.md> 执行 <阶段/完整计划>。

保持：<必须兼容的行为>。
允许：<可自主决定或重构的范围>。
验证：<targeted build/test/shot/validate 命令>。
除非遇到不可逆操作或计划冲突，否则自主推进到验收目标。
```

### 10.2 定位并修复问题

```text
现象：<具体表现>。
对照：<正常配置> 正常，<异常配置> 异常。
范围：<target / scene / platform / pipeline>。
怀疑：<可能的子系统；这是线索，不是强制结论>。
目标：<修复后的行为>。
保持：<不能破坏的现有行为>。
请先定位根因，再实现并用 <命令> 验证。
```

### 10.3 性能优化

```text
场景与规模：<数据量、分辨率、target>。
测量结果：<profile 热点、耗时、调用次数>。
当前猜测：<可能原因>。
目标：<可量化目标或至少不能回退的指标>。
约束：<显存、兼容性、代码复杂度>。

先建立基线并确认瓶颈，再优化；保留前后数据。
```

### 10.4 架构审核与计划

```text
审核 <目录/类/调用链>，重点检查：
- <依赖方向>
- <职责边界>
- <重复与特例>
- <正确性或生命周期>

先给出有代码证据的问题，再将最有价值的改动整理为分阶段计划，
写入 <docs/path.md>。本次不实施。
```

### 10.5 视觉和产品调整

```text
目标界面/场景：<target 和入口>。
参考：<截图或已有界面>。
目前问题：<层级、密度、遮挡、操作或风格>。
必须保留：<功能和交互>。
允许占位：<尚未实现的功能>。
用 <gnb shot/validate 命令> 验证，并检查实际截图。
```

模板的目的不是让所有提示词变长，而是提醒用户只填写能够减少不确定性的字段。没有信息的字段可以
删除，不要用空话补齐。

## 11. 团队落地方式

### 第一步：先改造仓库，不先培训“提示词技巧”

每个仓库至少具备：

- 一份简洁且准确的 `AGENTS.md`；
- 单目标构建和测试命令；
- 明确的成功/失败信号；
- `docs/designs`、`docs/plans` 或等价的任务外部记忆；
- 一条可快速执行的 smoke test；
- 大日志和产物的固定路径。

如果这些条件不存在，再好的提示词也只能让 Agent 更流畅地猜。

### 第二步：统一任务入口格式

团队先统一三个高频模板即可：执行计划、定位问题、性能优化。不要一开始建立复杂表单，否则填写
模板本身会成为新的协调成本。

### 第三步：按完成结果比较，而不是按消息数量比较

建议按周记录：

| 指标 | 计算方式 |
| --- | --- |
| 输入缓存率 | `cached_input_tokens / input_tokens` |
| 非缓存输入 | `input_tokens - cached_input_tokens` |
| 新增 Token 指标 | `非缓存输入 + output_tokens`，仅作内部相对比较 |
| 任务澄清轮次 | 开始执行前需要用户补充信息的次数 |
| 返工距离 | 错误方向产生到回退之间的提交或改动阶段数 |
| 验收产出 | 通过构建、测试或视觉验收的任务数 |
| 单位产出 Token | 新增 Token 指标 / 验收任务数，需按任务类型分组 |

不同模型、推理等级、任务类型和时间窗口的数据不能直接横向比较。尤其不要用“写了多少行代码”作为
唯一产出指标，删除无用代码和定位一处关键同步错误可能比生成大量代码更有价值。

### 第四步：复盘最高消耗的任务

每周只看消耗最高的少数任务，逐项判断：

- 是任务本身复杂，还是上下文反复丢失；
- 是合理的代码探索，还是缺少路径和复现条件；
- 是验证耗时，还是验证标准不明确；
- 是必要返工，还是错误方向停止太晚；
- 哪段知识应该沉淀到 `AGENTS.md`、guide 或 plan。

优化目标不是让每个任务都变短，而是让同类浪费不再重复发生。

## 12. 开始任务前的检查表

### 用户侧

- [ ] 这是当前 session 的同一目标吗？
- [ ] 已知的现象、对照组和范围是否写清楚？
- [ ] 复杂背景是否已有可引用文档？
- [ ] 哪些决策可以授权 Agent 自主完成？
- [ ] 成功后用什么命令或画面验收？
- [ ] 如果方向错误，回到哪个检查点？

### Agent 侧

- [ ] 先读仓库规则和指定计划，而不是重新猜架构；
- [ ] 搜索范围与用户提供的证据相匹配；
- [ ] 不把用户的怀疑当成强制结论；
- [ ] 只构建和测试受影响目标；
- [ ] 工具输出只保留与决策有关的部分；
- [ ] 遇到架构冲突或不可逆操作才暂停；
- [ ] 完成时报告结果、验证和残余风险，不复述全过程。

## 13. 统计方法附录

### 13.1 数据源

Codex Desktop 本地 session：

```text
~/.codex/sessions/**/*.jsonl
~/.codex/archived_sessions/**/*.jsonl
```

使用每个 `token_count` 事件中的：

```text
payload.info.total_token_usage
```

不要将所有 `total_token_usage` 相加，因为它是 session 内累计快照。

### 13.2 普通 session

```text
session contribution = 最后一个 total_token_usage
```

以下恒等式应成立：

```text
total_tokens = input_tokens + output_tokens
cached_input_tokens <= input_tokens
reasoning_output_tokens <= output_tokens
```

### 13.3 fork session

fork 文件会复制父 session 的历史。应通过当前 session 的第一个 `session_meta` 取得：

```text
id
forked_from_id
```

然后扣除与父 session token 序列相同的最长公共前缀：

```text
fork contribution = fork final usage - inherited prefix final usage
```

否则父 session 在多个 fork 中会被重复统计。

### 13.4 推荐派生指标

```text
cache_hit_rate = cached_input_tokens / input_tokens
uncached_input = input_tokens - cached_input_tokens
```

内部比较时可以计算：

```text
new_token_indicator = uncached_input + output_tokens
```

但它不是官方计费或 Codex 额度公式。订阅产品的实际消耗仍应以同一时间窗口内显示的额度变化为准。

## 14. 最终原则

高 Token 效率不是让 Agent 做更少的工作，而是让昂贵的推理始终落在值得解决的问题上：

- 稳定规则只解释一次；
- 复杂决策写入文档；
- 每次消息带来新证据或新决定；
- 可逆实现连续授权；
- 验证尽可能自动化；
- 核心假设失败时立即停止；
- 以通过验收的工程结果衡量效率。

当仓库本身容易被 Agent 理解、操作和验证时，节省 Token 会成为工程质量的副产品，而不是额外负担。
