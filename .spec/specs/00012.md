# #00012 让 gkNextRenderer 主管线原生运行在浏览器（WebGPU 后端）

## 背景与目标

希望让 gkNextRenderer 原生跑在浏览器中，以实现**快速迭代**与**快速分发**；同时桌面 Vulkan 端需要能**并行开发**，不被 Web 后端拖累。

经过对当前管线、shader、资源绑定模型的复盘，确认走 **Emscripten + WASM + 独立 WebGPU Renderer** 路线最现实——**不**引入 RHI 兼容抽象层（避免 Unity GfxDevice 那种 6 个月级别的重构），而是新建一个并列的 WebGPU 实现，架构镜像 `VulkanBaseRenderer` 但代码不共享。

核心依据：当前主管线是干净的 **Visibility buffer (raster) + Compute shading**，资源用法主要是 storage buffer / storage image / sampled image，全部 WebGPU 原生支持。唯一硬骨头是 [BindlessTexture.slang](../../assets/shaders/common/BindlessTexture.slang) 的 descriptor indexing 模型——WebGPU 当前规范不支持，需要做一次绑定模型重构。

## 范围

### In Scope

- 让 gkNextRenderer 主管线在支持 WebGPU 的浏览器（Chrome/Edge 113+ 优先）原生跑起来
- 至少渲染 `CornellBox.proc`、`MaterialShowcase.proc`、`LightingShowcase.proc` 三个 procedural 场景
- 桌面 Vulkan 端**零回归**，并行开发不受影响
- 部署到静态站点，产出可分发 URL

### Out of Scope（本期不做）

- PathTracing 管线（WebGPU 无 ray query）
- 真实 glTF / LDraw 场景加载（先用 procedural，回避资产 IO）
- 物理（JoltPhysics 在 wasm 不可用）
- 编辑器（`gkNextEditor`）
- 移动端浏览器适配
- DLSS / Streamline / 第三方 GPU 特性
- 多线程（SharedArrayBuffer 配置）

## 关键技术决策

### 1. 不做 RHI 兼容抽象层

桌面 Vulkan 与 Web WebGPU 是两个**并列**的 renderer 实现，架构镜像但代码不共享。理由：

- 抽 RHI 是 6+ 个月工程，相当于补 Unity 在 2005 年开始还的技术债
- GfxDevice 抽象的存在前提是"已有 5+ backend 要维护"；我们目前只有 2 个，做不划算
- 镜像架构能让两边演进时互相参考，不需要强一致

### 2. 共享层 vs 独立层

**保持 Vulkan-free（双 backend 共享 CPU 层）：**

- `src/Engine/Assets/` — FProcModel、Model、Vertex 等纯 CPU 资产
- `src/Engine/Runtime/` — ECS、组件、相机、命令历史（需先确认 Subsystems 已无 Vulkan 残留）

**Web 独立实现：**

- `src/Engine/WebGPU/` — 模仿 `Engine/Vulkan` 命名的薄封装（Device / Buffer / Pipeline / SwapChain）
- `src/Engine/Rendering/WebGPUBaseRenderer.{cpp,hpp}` — 镜像 `VulkanBaseRenderer`
- `src/Application/Render/gkNextRendererWeb/` — Web 入口

### 3. Shader 编译链

Slang 1.x WGSL backend 一次性建好，所有 `.slang` 在 build 时**同时**输出 `.spv`（桌面）和 `.wgsl`（Web）。CMake 自定义命令承担两份产物。

### 4. Bindless 模型重构（本期最大实质工作）

WebGPU 当前不支持 descriptor indexing。当前 `__DynamicResource SampleTextureArray[] / StorageTextureArray[]` + `NonUniformResourceIndex` 设计需要按用途拆分：

**StorageTextureArray（RT 寄存器，约 128 个）**

- 多数尺寸 = swapchain 分辨率，用法清晰
- WebGPU 端用 `texture_storage_2d_array`，layer 索引 = `RT_*` 常量
- Shader 改动最小

**SampleTextureArray（材质贴图，尺寸/格式不一）**

- 不能用 texture array（layer 要求同格式同尺寸）
- 短期：每帧根据可见材质组装一个 BindGroup，实例数据带 binding 索引
- 中期：等 WebGPU `binding_array` 提案落地（Chrome 实验旗标已可用），可恢复 bindless

> **连带收益**：这次重构对 Vulkan 端也是技术债清理。未来上 Metal 原生、或兼容更弱 GPU 时，绑定模型本来就要做。Web 化只是把这笔账提前还。

## WebGPU 与 Vulkan 能力差异（已确认）

| Vulkan 特性 | WebGPU 状态 | 本项目影响 |
|---|---|---|
| Bindless / descriptor indexing | ❌ 规范不支持 | **核心改造点**（见 §4） |
| Push constant | ❌ 不支持 | 换 uniform buffer，Slang 自动处理 |
| u32 atomic | ✅ | `InterlockedAdd` 直转（GpuCull 用） |
| u64 atomic | ❌ | 本项目未使用 ✓ |
| Storage buffer / storage texture | ✅ | GPUScene、RT 布局保留 |
| Sampled texture + Sampler | ✅ | OK |
| 多目标渲染、render attachment | ✅ | Visibility pass 直转 |
| Subgroup ops | 🟡 Chrome 128+ 实验 | 本项目未使用 ✓ |
| Ray query | ❌ | PathTracing 不能上 Web（已 out-of-scope） |
| Bind group 数量上限 | 4 个 | 需重组绑定布局时算账 |

## 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| Slang WGSL backend 对 bindless 转译失败 | 整条 shader 链要手写 WGSL 或加翻译层 | **W0 spike 先验证**，本任务可执行性的前提 |
| `vcpkg sdl3` 没开 emscripten triplet | 失去窗口/事件抽象 | 直接用 `<emscripten/html5.h>`，不上 SDL3 |
| `vcpkg imgui` 没 wgpu backend feature | UI 跑不起来 | 手动把 `imgui_impl_wgpu.{h,cpp}` 加到 `src/ThirdParty/imgui-custom/` |
| WebGPU 4 bind group 上限挤不下 | 需要重组绑定布局 | 设计时算账，必要时合并相关资源到同一 group |
| 包体过大 | 冷启动慢 | `-Os` + 静态库 LTO + 排除 cpptrace/whisper/joltphysics |
| Subsystems 仍 include Vulkan 头 | 共享层假设破产 | 先做 [phase-10-vulkan-facade](../../docs/plans/2026-05/refactor/phase-10-vulkan-facade.md) 或本任务内顺手清掉 |

## 并行开发约束（强制）

1. **`src/Engine/Assets/` 和 `src/Engine/Runtime/` 必须保持 Vulkan-free**——这两层是双 backend 共享的 CPU 层
2. **CI 必须新增 `cmake --preset web && emmake -j` 校验**——任何引入 Vulkan 头到上述层级的 PR 自动红
3. **桌面端 `Engine/Vulkan` / `Engine/Rendering` 继续自由演进**，不需要为 Web 写适配
4. **新加 Vulkan 调用前，先确认是在 Vulkan 专属层**（`Engine/Vulkan`、`Engine/Rendering/Vulkan*`）
