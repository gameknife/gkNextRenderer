# 预制件场景搭建工作流

## 目的

这份文档约束 `CharacterPlayground.proc` 以及后续 KayKit 程序化场景的搭建方式。

目标不是一次性把大场景堆满，而是把场景拆成一组经过人工审核的预制件，再将预制件摆放到场景中。这样可以显著降低坐标错位、斜坡朝向错误、层级错放、实例漏摆等问题。

## 当前结论

后续 AI agent 在搭建 KayKit 场景时，默认遵循以下流程：

1. 先把场景简化到只包含当前待审核的预制件。
2. 一次只做一个预制件，不同时推进多个复杂结构。
3. 预制件通过人工审核后，才允许进入下一组预制件。
4. 大场景布局必须使用“预制件锚点摆放”，不要重新回到散乱的绝对坐标堆砌。

## 核心规则

### 1. 预制件优先，禁止先拼大场景

- 不要在 `CharacterPlayground.proc` 中直接堆几十个散点 `placePiece(...)` 来拟合参考图。
- 先把参考图拆成独立结构，例如：
  - 星星柱
  - 连续通道
  - 弹簧挑战组
  - 终点塔
- 每个结构先单独摆在空场景里校准。

### 2. 一个预制件一个预制件地审

- 当前用户已经明确要求：先清空场景，只审单个预制件。
- 如果当前预制件还没有被确认正确，不要继续加下一个。
- 如果用户反馈“不太对”，优先继续修当前预制件，不要并行引入新结构。

### 3. 预制件内部必须使用相对坐标

- 预制件内部使用相对偏移，不使用分散的世界坐标。
- 推荐模式：
  - 定义 `PrefabPiecePlacement`
  - 用 `placePrefab(prefix, anchor, rotation, pieces)` 摆放
- 预制件内部零件的相对关系应该稳定，场景中只改锚点和整体朝向。

### 4. 预制件外部才允许使用锚点

- 场景布局层只负责：
  - 选择预制件
  - 指定锚点位置
  - 指定整体旋转
- 场景布局层不应该重新手工调整预制件内部某一块平台的位置。

### 5. 先保证视觉正确，再扩展玩法

- 对照参考图时，优先匹配：
  - 主体轮廓
  - 高差关系
  - 主要支撑结构
  - 明显装饰位置
- 在预制件轮廓未稳定前，不要急着加额外路径、收集物、导视或障碍物。

### 6. 对可变高度结构，优先做“同模板多高度”

- 像星星柱这种结构，本质是同一个预制件模板，只是撑杆高度不同。
- 优先通过替换已存在的高度件来做变化，例如：
  - `pillar_1x1x2`
  - `pillar_1x1x4`
  - `pillar_1x1x8`
- 不要为高度差写三套完全不同的布局代码。

### 7. 场景调试时保持背景干净

- 审核单个预制件时，场景中只保留：
  - 地面
  - 出生平台
  - 当前待审核预制件
- 避免旧结构遮挡视线，影响判断。

### 8. 静态碰撞遵循 mesh collider 路径

- 静态 KayKit 件不要手工创建 AABB `CreateBoxBody(...)`。
- 只挂 `PhysicsComponent`，交给场景统一走 mesh collider。
- 这条规则对斜坡尤其重要，否则角色会在斜面上悬空。

## 命名约定

### 预制件名

- 使用语义化名称：
  - `StarPillar`
  - `SpringArea`
  - `FinishTower`
  - `ChannelRun`

### 实例名

- 场景中的单个实例用：
  - `StarPillar_Short`
  - `StarPillar_Medium`
  - `StarPillar_Tall`

### 预制件内部零件名

- 统一使用 `前缀 + 后缀`：
  - `StarPillar_Medium_Base`
  - `StarPillar_Medium_Pole`
  - `StarPillar_Medium_Top`
  - `StarPillar_Medium_Star`

## 当前已确认的工作方式

截至当前版本，`CharacterPlayground.proc` 已经切换到“预制件优先”的搭建方式，且场景已被收缩成单预制件审核模式。

当前已通过人工确认的预制件：

- `StarPillar`
  - 组成：底座、撑杆、顶部木平台、星星
  - 已验证存在短/中/高三种撑杆高度
  - 适合作为后续平台化装饰件模板

## 已沉淀的预制件经验

### `Scaffold` 架子预制件

- 先拆“视觉语义”，不要先猜零件名。
- 参考图中的结构应先抽象成：
  - 左塔架
  - 右塔架
  - 左顶托方板
  - 右顶托方板
  - 中间跨接长板
- 不要把它简单理解成“两个支架 + 一整块长顶板”。

- 选件时优先看 AABB 和形态，不要只看资源名。
- `structure_A`、`strut_horizontal`、`strut_vertical` 不能仅因名称像“支撑件”就默认作为塔架主体。
- 当前实践中，`structure_C` 更适合作为脚手架塔段，因为它的高度和轮廓更接近参考图中的立式支撑结构。

- 顶板必须按“支撑关系”摆，不要按“覆盖面积”摆。
- 正确的顶板关系是：
  - 左塔上方一块 `floor_wood_2x2`
  - 右塔上方一块 `floor_wood_2x2`
  - 中间一块 `floor_wood_2x6` 连接两侧
- 如果直接放一整块长板，通常会在视觉上与塔架错位，也更难判断局部偏差来自哪一部分。

- 顶板高度对齐时，要看接触面，不要只看模型中心。
- 如果参考图里三块板在同一层，那么三块板的 `y` 标高也应一致；不要把中间跨接板额外抬高一层。

- 预制件初调阶段，优先先做对称和基础对齐。
- 在轮廓稳定前，不要过早加入左右高低差、倾斜、额外装饰或复杂支撑细节。
- 先把“塔架中心是否正对顶板中心”“左右是否同高”“三块顶板是否共面”校准，再决定是否做非对称微调。

- 对这种结构，推荐先做一个最小正确版本：
  - 两组塔架
  - 两块方板
  - 一块长板
- 审核通过后，再考虑追加按钮、宝石、额外斜撑等附属元素。

## 推荐执行顺序

后续 agent 修改 KayKit 场景时，按下面顺序执行：

1. 打开参考图，选定一个结构。
2. 清空干扰结构，只留下当前预制件测试环境。
3. 用相对坐标搭建该预制件。
4. 运行并等待人工审核。
5. 审核通过后，再进入下一个预制件。
6. 当多个预制件都通过后，再进行大场景拼装。

## 验证要求

每次改动后至少做以下验证：

1. `./build.bat --preset full-windows`
2. 运行 `CharacterDemo --load-scene CharacterPlayground.proc`
3. 确认日志出现 `uploaded scene [CharacterPlayground.proc] to gpu`
4. 确认没有新的 `failed to load piece` 或 `failed to parse gltf file`

## 失败时的处理原则

- 如果预制件开始变乱，先回到单预制件极简场景。
- 如果多个问题叠在一起，先修轮廓和朝向，再修装饰。
- 如果用户明确说“先不要复杂场景”，不要私自把已审核预制件重新塞回大场景。
